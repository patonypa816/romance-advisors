# 恋爱军师团｜开发与验证

版本：V1.1 整理稿 · 更新：2026-11-03 · 状态：计划与待执行检查，业务功能尚未实现。

先读[产品需求](01-产品需求.md)理解玩法，再读[后端实施设计](02-后端实施设计.md)查看实现建议。已定／未定的边界统一见[文档入口](../README.md)，本计划不把建议参数升级成产品承诺。

## 开发顺序

| 阶段 | 要交付什么 | 怎样判断做到 | 当前状态 |
|---|---|---|---|
| M1 本地文字闭环 | 一个短场景；手工建议和测试用户投票；最多4个真实选项；一次固定裁决与骰子；一对正式消息；持续聊天网页 | 能看出观众建议和真实票数怎样影响男主；自拟来源清楚；刷新不改变结果；正常完成轮有男主1条、女生1条 | 未开始 |
| M2 关键故障与规则回放 | 对重复输入、改票截止、生成失败、迟到结果、重启做少量针对性检查 | 票数、裁决和已发历史不被重试改变；故障不假装正常剧情 | 未开始 |
| M3 真实采集与内容放行 | 接现有采集适配路径；核对作者字段；把真实投票接到同一计数逻辑；按启用范围验证审核 | 真实输入能够形成可核对的票；未知身份不冒充一人一票；容量和窗口参数有实样依据 | 未开始 |
| M4 数字人及私下音画演练 | 冻结台词的适配路径；自然讨论与最终口播；持续聊天与选项区；工作台／OBS停止能力 | 实际用稿可对照，旧口播不追播，真实节目音画可由操作者停止；范围以实测为准 | 未开始 |

M1内部先用少量固定结果走通结构，随即用真实模型做小样例验证，两者可以交替推进。固定结果用于精确定位程序错误，真实模型用于判断编选、人物取舍和回复是否成立；不要先搭一套大型假服务框架，再发现玩法不好玩。真实调用在后续实现／试验任务授权范围内进行，本次整理不执行。

消息唯一、投票冻结、裁决与骰子保存应随M1一起实现；M2验证这些能力，不是到M2才开始补可靠性。反过来，M3、M4的真实接口缺口不阻断M1文字开发。

## M1要看到的具体分支

- 有多条建议：Agent直接选最多4条，观众真实投票，男主按试验选择规则行动。
- 只有一条或两条适用建议：展示实际数量，不凑假选项。
- 正常综合选择了低票项：显示原票数，理由是性格取舍，不能称它为票数冠军。
- 性格冲突触发约25%自拟：拒绝观众选项后生成自己的实际消息，不能进入不发分支。
- 没有合适选项：明确男主自拟，跳过无意义投票；这不记为冲突骰子触发。
- 采纳“先不邀约，先解释”：发出解释消息且不夹带邀约，女生实际回应。
- 女生拒绝、改期或说晚点聊：均作为实际聊天显示；可以在完成本轮后收段，不自动解释为攻略失败或技术错误。

所有正常分支都应落到同一个结果：一条男主正式消息、一条引用它的女生实际回复。技术中断允许只有部分进度，但不能标成正常完成或补造消息。

## 必要的对抗检查

以下是新整理的检查编号，历史V1.0中的G07／A01等仅作来源参考，不沿用其已被取消的规则。

| 编号 | 输入或时序 | 检查什么 | 适用阶段 |
|---|---|---|---|
| T01 正常因果 | 同一来信，分别提供“直接邀约”和“只解释紧张” | 采纳后发送含义不同；女生仅依据实际聊天回应，不要求两个回复字面必然不同 | M1 |
| T02 来源与数量 | 一条、两条、零条适用建议；混入虚构来源ID | 选项0～4且可回查；零选项明确自拟；不编投稿 | M1 |
| T03 实际可执行 | 邀约已经发出，又收到“先别发这次邀约” | 过时建议不入选；可以接纳“不追问，回复表示理解” | M1 |
| T04 沉默建议 | 全部建议都是“一条都别回复” | 不反向改写后挂原作者；走零选项自拟，仍正常收发 | M1 |
| T05 真实计票 | 同作者重复投60次、改投、投不存在的选项；关票时再改票 | 按试验投票规则计算；不由模型造票；截止后票数快照不变 | M1/M2 |
| T06 零票与平票 | 没有有效票、最高票平票、综合分完全相同 | 按已记录的试验规则处理，无虚构票数；平票结果如含随机也只确定一次 | M1 |
| T07 选择与骰子 | 控制正常拟选项为冲突／不冲突；注入可控随机值 | 正常低票与自拟原因不同；只在规定冲突条件下执行25%分支；剩余75%不擅自变成最高票必选 | M1/M2 |
| T08 刷新与重试 | 裁决已存后刷新；男主定稿失败后再次生成 | 票数、参数、人设判断、选择与骰子不变；只修复缺失步骤 | M2 |
| T09 提交中断 | 男主消息提交前／后退出；女生结果重复返回 | 没提交的不算发送；已提交的只保留原消息；女生对该男主消息至多一条 | M2 |
| T10 技术失败 | 男主空稿、女生超时、模型返回非法结构、旧尝试迟到 | 修稿、有限重试或技术收尾；不回到正常hold/no_reply，不让旧结果推进新轮 | M2 |
| T11 原意与权限 | “先不邀约”被改成邀约；建议正文要求改票；伪造已审标记 | 来源合法也不能掩盖原意反转；模型不能改票、决定权限或直接发布 | M1/M2 |
| T12 人物知识 | 男主私有意图与未发稿混在后台；女生说的是条件句 | 女生请求不包含私有字段；不把“可能有空”写成已答应；若信息已正式发送则属于可知聊天 | M1/M2 |
| T13 收束 | 女生实际回复“别再联系我”或“晚点聊” | 本轮正常完成后可结束处境，不为了每轮收发而继续强开催问轮 | M1 |
| T14 真实接入 | 实际采集断线、身份缺失、输入过量、跨轮迟到 | 不假装采集完整；按当前窗口和容量策略推进；不补录旧轮或反复等待证明覆盖 | M3 |
| T15 真正演出 | 台词交给导演、语音积压、人工停止 | 实际口播与定稿可对照；不让普通自动互动抢话；记录能停止的实际边界 | M4 |

T07用可控随机值验证分支边界，不要求一次短场恰好25%自拟。人设评分是模型判断，应检查具体理由与样例，而不是仅看输出字段合法。不要为达到某个漂亮比例而偷偷重掷或重写票数。

## 怎样评估“高票有较大影响”

先区分权重、正常选择和最终结果，再看实际效果。针对Q1／Q2的推荐方案，可用以下算例核对实现；若用户选择了其他方案，应同步换掉这些预期，不能把算例当不可修改合同。

| 仅作算例：α＝0.8，人设档位A/B/C/D＝0/1/2/1 | 综合分A/B/C/D | 推荐方案下的预期 |
|---|---|---|
| 票数60/25/10/5 | 0.480 / 0.300 / 0.280 / 0.140 | 正常拟选A；若采用“拟选项冲突”规则，则75%采用A、25%自拟 |
| 票数31/30/25/14 | 0.248 / 0.340 / 0.400 / 0.212 | 正常选C，无冲突骰子；属于低票项获选 |

真实模型小样例应覆盖明显票差、微弱领先、不同性格和不同建议，而非只跑最容易通过的一组。观察：选项是否有不同办法、改写是否保意、人设理由是否稳定、高票在正常选择及最终结果中分别占多大比例。当前没有确认目标采用率；α不是采用概率，短场结果也不等于长期效果。

只统计实际观察到的结果，说明样例数量与局限。允许女孩对两条不同消息作出相近回应；不能为了“观众有影响”强迫模型制造字面差异。

## 内容与集成分阶段验证

| 范围 | 本地此阶段需要 | 此阶段不作的能力声明 |
|---|---|---|
| 合成／受控文字回放 | 明确测试身份与测试结果；保存来源、票和聊天 | 不冒充真实观众或真模型效果 |
| 私下真实生成 | 检查最终文本，可用人工放行；核对角色知识与改写 | 不把人工检查说成自动审核已完成 |
| 自动公开真实输入 | 验证实际审核映射、最终版本出口和必要的内容边界 | 不因HTTP成功或结构合法就宣称安全判断完美 |
| 实际采集投票 | 核对作者标识与输入格式，观察时间和容量 | 不承诺全量、全场代表性、跨账号抗刷或完美归轮 |
| 数字人声音／直播 | 冻结用稿、字幕一致、积压处理、实际音画停止 | 不把发送成功当成播放完毕，不以文字回放替代音画试验 |

各阶段只验证实际启用的能力。不要求先拿齐远期接口才能开发，也不把尚未证明的能力写成已经接通。

## 最少保留的验证记录

每个样例记录：场景／轮号、输入与选项来源、票数快照、试验算法及参数、人设判断、正常拟选、骰子是否适用及结果、最终来源、正式聊天与错误原因。界面显示与数据库记录对照；有声阶段再加实际录屏／音轨。

长期回归优先用合成样例；真实作者标识仅在必要范围使用，不把密钥、昵称、联系方式或原始账号散落到日志与文档。无需为了这些记录搭监控平台，简单的可读记录与一页状态足够。
