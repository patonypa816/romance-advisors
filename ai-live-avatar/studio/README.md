# 御书房 · 直播工作台

本机应用：工作台管弹幕、台词、动作和会话，OBS 单独接收数字人音画。打开应用不会开收费云场，也不会替 OBS 公开推流或录像。

默认口播已接入同次语音时间戳与语义动作锚点，覆盖观众回复和主持口播；纯动作保持独立入口。详细边界见文末“正式语义动作流程”。

语义口播段落现可带可选`ssml`，原有`text/instruction/actions/recovery`不变。`speech_markup.py`统一解析正文与读法，TTS明确开启SSML；字幕保留`text`，Type10使用独立朗读文字。当前支持`speak`整段rate/pitch/volume、`break/sub/phoneme/say-as`；多个speak需相同有效韵律参数，不接入声效、BGM或临时换音色。3.1 Flash实测需将整段韵律同步写入HTTP参数。多段词时间只接受供应商已有的连续全局索引/时间，不猜偏移；发音改写区暂不作动作锚点。细节与真实小样见[SSML接入验收](../../romance-advisors/artifacts/ssml-integration-20261104/验收记录.md)，本次尚未启动Vidu做视觉验收。

正常对话默认使用 A 编排：独立 GE（眼神、表情）提前 1.1 秒，S（短动作）后 1.5 秒发送 Q（仅眼神和表情），Q 后至少 1 秒才发送下一条 Type9。语音合成完成后，以同次真实字时间戳生成合法候选，多套候选时由 Qwen3.8-Flash 选择最终动作位置，只有一套时直接采用并做相同终检；相邻 S 至少间隔 3.6 秒，所有 S 仍在语音结束前，末尾 Q 可在语音后自然收尾。动作等待不占用音频通道。S、L、Q 成功写入后至少 1 秒的保护也继续适用于历史试验；历史 L/0.5 秒与固定 A/B 入口保持原规则。A 的原发送间隔已通过用户样本评价，本轮放开尾 Q 后的画面效果仍须实播观察；计划与发送不表示视觉完成。

## 本轮审查落实（2026-11-02）

Q只发送眼神和表情，与 GE 一样不发送肢体动作；名称、发送节拍和模式结构保持不变。`recovery.gaze` 只写眼神，`recovery.expression` 只写可见表情，不写姿态、肢体或过渡动作，并保留角色化情绪。需要主动动作或明确返回时写入 S/L，不交给 Q；不按发送记录推断人物已经归位。读弹幕的 R/S0 是程序固定的阅读与主动返回，独立待机动作库按自身配置执行，两者不属于本次 Q 内容调整。历史归档和原始样本不改写。

当前大脑只处理文字角色设定、评论和发送历史；正常语音及纯动作合同均不再包含 `observation`。旧固定回放使用明确的历史解析入口，保存的计划和音频哈希不改写。眼神、表情与主动动作仍是发送目标，系统不能据此判断人物实际姿态。

内容可用性与用量统计分开：完整音频／合法正文可以继续使用，用量缺失或格式异常显示“未核实”，已知费用只作为小计，不将未知记为零。发送前的单条失败不再冻结整场；已经尝试发送后的异常、工作循环失效、播放器停帧及收费创建／结束状态不明仍保留原保护。可靠确认结束的历史场次无需每次开场联网复查。

正常动作回执只记录实际发送；`handoff_wait_elapsed` 表示本地交接等待已结束，不能当作播放完成。通用资产页的手动形象切换由操作者确认，标记为 `operator_confirmed`；《恋爱军师团》六档外观走下述自动衔接。网页只接收显示所需字段，完整内部调度依据仍写会话归档。

选中资产后，角色语气统一在资产页编辑，顶部菜单提供入口；无选中资产时仍可编辑默认角色。没有实现的资产声音选择和本地录像验证占位已移除。历史实验入口和根目录独立旧工作台仍保留，本轮不改实验时序或归档素材。

## 礼物反馈与入场欢迎（2026-11-02）

直播页新增“礼物与欢迎”面板，可编辑默认礼物动作、感谢词、精确名称／别名、可选礼物ID、动作部位、只做动作模式及冷却。默认小心心点头、鲜花手放胸前、棒棒糖竖拇指等；未配置礼物使用可关闭的点头兜底。已有ID规则优先，空ID规则按精确名称匹配；关闭一条命中的规则会略过该礼物，不再降级到兜底。感谢词由可编辑模板生成，沿用当前角色音色；不调用评论回复模型改写措辞。语音后的动作定位仍走现有词时间核验与A方案，动作和 Q 发送间隔未改变。

欢迎仅认 `user.payGradeLevel`（采集器 `User.payGrade.level`），必须严格大于10、成员事件 `action=1` 且非任命管理员；未知时不猜。不判断停留秒数，也不增加相应等待。合格入场立即成为候选，选中时冻结整个有效批次；少量代表昵称加集体欢迎覆盖整批，长昵称可使用集体表达。仅整轮必要信号发送完成后记本场已欢迎，入队和准备成功均不计完成。新入场者进入下一批，冻结成员不会重复入选。待选欢迎60秒、礼物120秒过期；选中后改为120秒准备期限，开始发送后不再因准备期限到期失效。失败未发送可有限释放一次，部分发送不重放。暂停、断线与设置变化清后续，当前已开始轮可正常收尾；换场清空本场记录。

评论、礼物、欢迎由同一大脑选择下一轮，评论最多合并3条、礼物最多合并3组，欢迎最多点3个代表名字但覆盖整个冻结批次。类别持续有候选却让过两轮，进入本地保底，最早可调整的轮次优先照顾等待最久者；无候选不积攒额度。正式计数只按完整发送更新，当前轮对提前选择的影响仅作预测。正常自动编排最多当前轮加一个后续准备槽，普通新事件不撤销已准备内容；明确人工主持仍可优先。纯动作礼物无独立前导时与评论拆轮，避免覆盖评论动作。

礼物保留消息与连击组去重、配置动作和冷却；多组感谢只选择一个配置动作，其他动作明确记作合并取舍。不相乘、不朗读未经核实的数量。组号缺失时至少15秒冷却。统一编排继续共用原音频／动作发送器与原Type9间隔。新旧方案及在线能力边界见[统一互动编排方案](统一互动编排方案-2026-11-02.md)。

礼物与欢迎共享120条有界待选池；消息去重最近4096条／120秒，连击组2048条／600秒保护，超出容量明确略过。默认“本场一次”的已完成欢迎身份单独保留，内存随本场实际覆盖人数增长。

“检查规则”默认只在独立临时队列中生成预计台词和动作，未开云场也可使用，不调用LLM/TTS、不播放。取消“只检查规则”后才会加入本场队列，要求用户已手动开场且音画就绪；实际执行语音、动作仍有原来的云服务用量。修改并保存规则会撤销未开始发送的旧互动，已开始的一轮保持原快照。专项试验和固定回放模式不开放此功能。

采集器源码和dist已补齐gift/member字段，工作台订阅chat,gift,member,roomStatus。前一轮已完成10分18秒公开房间评论／入场联调，礼物另做模拟；本次调整先做离线与本地信号回放，真实礼物采集仍待验证。清唱尚未接入；“清唱后统一反馈”待清唱通道实施后再验收。

## 待机小动作（2026-11-01）

直播页“待机小动作”接入 Vidu 动作库，目前为朱元璋准备了轻微侧头、放松肩背、手指舒展、短暂垂眸四项。画面效果由操作者试播核对，工作台不维护没有确认入口的“已验证”状态。服务启动及每场默认关闭；先手动开场，逐项点击“单次试播”观察，再开启随机待机。动作库刷新和每次启用都会只读核对远端 ID、名称及描述摘要，不自动生成或改写动作。描述有变化时只停用待机，不阻止语音或主讲。

独立待机动作库有自己的回正配置（日志也标作 Q），不经过上述口播 Q 编译。默认连续空闲 15～25 秒后随机挑选动作，保持 3 秒后发送一次该库配置的回正；同一动作冷却 60 秒，多项启用时不连续重复，单项启用时可在冷却后重复。间隔及勾选可在关闭后保存。待机不调用模型或语音合成，也不发送静音。

候选弹幕与筛选阻止新动作；已选回复、主持安排及正在运行的主讲会提前结束待机动作，回正后再让位。主讲暂停且当前发送结束后允许重新计时；忙碌会清掉计时，不补发错过的动作。动作 I 到 Q 至少 1.1 秒，Q 后至少 1 秒再开始业务内容。旧 D 待机的界面、接口和循环已移除，历史场次记录保留。

Q 失败会关闭待机并锁住后续表演，需在面板显式“回正”或“关闭待机”处理；普通回复或形象切换不会自动重试失败 Q。换形象会先关闭并按该库独立配置发送回正，之后不会自动再启用。停场阻止后续动作，不为了补 Q 延迟停场；已进入网络的在途请求无法撤回，其结果须按日志和画面核对。

本地已审阅配置在 `data/idle-action-library.json`，每场发送记录在 `idle-motions-log.json`，新模块源码纳入场次快照。记录的 I/Q 成功仅表示本机完成发送；人物、手部、服装、动作幅度和回正衔接仍需实际试播验收。

## 打开

双击 `启动工作台.command`。它使用本仓库 `.venv`；已有同一工作台运行时只打开原地址，不创建第二个服务。首次使用随机本机端口，之后保留该端口和播放器地址，方便 OBS 复用。服务仅监听 `127.0.0.1`，只开放明确列出的接口和静态文件，不暴露项目目录。

也可从仓库目录运行 `.venv/bin/python -B studio/server.py`，根据终端输出打开工作台。端口被其他进程占用时退出，不自动换到另一地址或关闭其他进程。

### 临时工作台预览

手动弹幕联调时，可在本机服务停止后运行 `.venv/bin/python -B studio/server.py --preview`，再在 Codex 内置浏览器打开工作台。此选项只作用于本次进程，不修改 OBS 配置；正常重启恢复 OBS 接收。服务端只向预览页授予唯一播放器资格，普通 OBS 页不能同时入会。打开页面仍不自动创建云场。

最小短表演试验需显式运行 `.venv/bin/python -B studio/server.py --preview --short-performance-test`。它仅本进程生效，不保存到 `local.json`；正常启动使用正式语义动作流程。用户手动开场后，可使用「模拟弹幕」「一次安排」或「只做动作」；真实评论来源与主线仍禁用。模拟弹幕走普通观众回复，不改写为主持指令；有语音时模型计划须 `reading=null`、一段台词、一个S节点及一个motion，纯动作沿用无台词合同、同样只接受单S及单motion；超出范围明确拒绝且不会自动重试。三种入口均为只有眼神/表情的GE前导 → 从GE成功写入后0.5秒发S → 从S成功写入后1.5秒发原recovery的Q。有语音时从S成功写入开始Type10和PCM，Q与声音并行；纯动作不读取语音凭据、不调用TTS、不发送Type10或PCM。停止会取消未发出的后续内容。这里的时间仅证明本机发送顺序，云端画面与口型需在工作台及录像中验收。每场 `brain-context.json`、`variant.json` 和纳入源码manifest的 `source-used/run-mode.json` 留下模式证据。

连续口播双动作组试验运行 `.venv/bin/python -B studio/server.py --preview --continuous-speech-test`，与 `--short-performance-test` 互斥且只对本进程生效。仅开放模拟弹幕与一次安排；真实评论、主线、纯动作及 reading 均拒绝。模型仍输出一段不超过30字的完整台词，由一次 TTS 合成为同一份 PCM，动作计划恰好两个单 S，首间隔0、第二计划间隔3秒。每组独立 GE→0.5秒→S→1.5秒→Q，Q只发送眼神和表情；第一 S 成功后发送唯一 Type10 并连续送音频。第二 GE 同时等待前 Q 成功、本机首 PCM 成功后2.5秒和累计已发送2.5秒 PCM；它之后的 S/Q 继续从实际写入重新计时，不追赶压缩组内间隔。整段结束后才进行一次缓冲等待。真实 PCM 少于5秒时，在任何动作/台词/音频发送前拒绝并显示具体时长；不自动重试、不补静音、不改变正常语速。时间和进度只证明本机发送事实，连续听感与动作仍需工作台及录像验收。每场归档包含模式、两个动作组、计划/实际时间与唯一音频发送记录。

长文多动作试验运行 `.venv/bin/python -B studio/server.py --preview --long-speech-test`，与前两种试验互斥。主持仍可输入600字，模型按完整描述生成一段最多120字口播，优先遵守本轮明确篇幅与关键信息，角色的常规“简短”偏好不能覆盖它。动作按内容选择1至6个单S组，不固定两个；每组沿用GE→0.5秒→S→1.5秒→Q，后续S计划位于口播开始后的3、6、9…秒，GE提前0.5秒并等前Q成功与真实PCM进度。仅一次TTS与一个Type10，音频上限仍30秒。N组要求真实PCM至少 `(N-1)*3+2` 秒（末尾Q的1.5秒加0.5秒音频余量），不足时在任何发送前明确拒绝，已发生TTS用量仍保留；不裁字、不删动作、不加静音、不自动重试。输入/原生成结果均归档，回复卡显示生成字数与动作组数。120字和1–6组都是本轮本机试验范围，不是平台能力上限。旧30字双组版仍可用原启动参数复现。

固定素材5秒对照使用 `.venv/bin/python -B studio/server.py --preview --long-speech-test --replay-source studio/data/runs/20261031-154919-241d27 --replay-comment c0001`。它只在当前进程启用，复用原场次c0001的74字台词、17.36秒PCM/WAV及四组动作，只有后续动作的组间距由3秒改为5秒；GE→S仍0.5秒，S→Q仍1.5秒，四个S计划相对首S位于0/5/10/15秒，音频门槛17秒。启动前验证原计划、发送回执、音频字节/哈希、数字人ID与底图；每场保存只读replay-source快照。用户开场后手动点击“播放对照样本”，不开场不播放；同一请求重传不重复入队。固定模式拒绝普通输入和角色修改，绕开LLM/TTS及语音凭据，不增加TTS用量；Vidu会话仍由用户手动开始并按原规则结束归档。正常启动和原3秒长文模式保持原行为。

单L描述对照在上述固定回放命令后添加 `--replay-long-action`。仍只读核验并复用原c0001的17.36秒音频与台词，将四个动作的原文按顺序合成一条L描述（whole_body），眼神/表情使用原第一组，末Q使用原recovery。仅发送GE→0.5秒→L+一次Type10/连续PCM→从L成功写入起17.36秒后Q，总计3条Type9；没有中间S或Q。L是本机动作类别，线上仍为Type9，不代表平台存在独立L接口或保证按描述完成。该试验同时减少帧数并改变动作描述组织方式，画面改善不能单独证明Type9限额。原3秒/5秒多S模式保持不变。

双L分组对照在单L命令后再加 `--replay-long-action-groups 2`。原四个S描述按顺序每两项用“，同时”合为一个L，各组GE取原第1/3个S的眼神表情，两Q都用原recovery；原台词与17.36秒PCM/WAV不变。以首GE为0，计划时间为GE1=0、L1=0.5、Q1=8.18、GE2=8.68、L2=9.18、Q2=17.86秒；L1窗口7.68秒，L2窗口8.68秒。第二GE同时等待Q1成功后至少0.5秒、首PCM成功后8.18秒以及已发送8.18秒PCM，第二L再从GE2成功后等0.5秒，末Q从L2成功后等8.68秒；延迟不追赶、不压缩间隔。全程仅一次Type10、连续原PCM和6条Type9，停场取消未发节点。这些时刻是本机发送安排；眼神表情能否延续及双L是否自然衔接需用户试播。

双L提前Q对照在双L命令后再加 `--replay-first-q-after 3`。唯一动作计划变化为第一L的hold_seconds从7.68改为3；原音频、台词、两条L描述、两组GE与两Q内容、第二L起点8.68和窗口8.68均保持。相对首GE计划为0/0.5/3.5/8.68/9.18/17.86秒，第一Q至第二GE等待5.18秒、再等0.5秒发第二L；仍按成功写入计时，不追赶压缩。此参数只在当前双L进程生效，省略即可复现原7.68秒对照。

第二L语义位置对照在提前Q命令后加 `--replay-second-l-at 7.36`，仅允许双L且 `--replay-first-q-after 3`。将第二L从原音频8.68秒移到已听辨的“百废待兴”7.36秒，第二GE相应为6.86秒，末Q仍在音频17.36秒结尾，故第二L窗口从8.68变为10秒。相对首GE计划为0/0.5/3.5/7.36/7.86/17.86秒；原音频、台词、六条指令内容与第一L→Q的3秒保持。后续等待仍以成功写入计时，不追赶压缩；7.36秒表示发送目标，不能保证画面动作在该词处立即出现。省略新参数即可复现原8.68秒方案。

预览内的“开启声音”按钮用于恢复浏览器拦截的 SDK 音频播放；音轨在线不等于扬声器已实际出声。测试时保持工作台打开，刷新或关闭会释放播放器并触发停场。结束后先核对云端结束与录像归档，再退出服务。

## 主持指令与主讲话题

音画就绪后，在统一的“输入与执行”区输入内容。“模拟弹幕”走观众回复流程（最多 160 字）；以下主持方式最多 600 字。同一 Qwen3.8-Flash 模型按独立主持规则生成计划；它不会把主持原文当观众弹幕朗读，也不会先回答“收到指令”。

- **主动安排**：生成一轮角色台词及动作，执行一次后停止，例如“语气郑重，提醒大家珍惜粮食”。
- **主讲话题**：指定 1–6 个完整小段，先生成有限提纲，再逐段讲述；每个主讲小段是一份最多120字的完整台词。观众互动持续优先，只有没有待筛选或待回应互动时才推进；可以一直顺着弹幕聊向其他内容。话题讲完后完成待命，不自动扩展；“继续主讲”只恢复手动暂停，完成或停止后需要新安排。
- **只做动作**：模型只输出 S/L、G/E 和眼神表情目标，执行器只发送主动动作与尾部 Q；Q只发送眼神和表情，不调用语音合成、不用静音或假台词占位。每组最多 6 个主动动作，时间与部位冲突规则沿用原合同。

主动安排和纯动作在下一轮边界优先于等待中的普通弹幕。重新提交“主讲话题”即换题；新题、暂停、停止会撤销尚未开始发送的旧主线任务，包括迟到模型结果和已生成但未发送的计划。已经开始发送的一小轮正常收尾，云场“结束会话”仍具有更高优先级。普通“暂停接单”暂停观众输入并撤销未发礼物／欢迎，原已选评论继续；主线有独立暂停按钮。

下一段台词、语音和动作排程可以与当前讲述重叠；自动编排共用一个后续准备槽，主持明确安排仍可优先。预备内容与本场、主题版本及前驱绑定，准备好不代表已经讲过或取得发送资格；发送仍只有一路，继续等待原有尾Q和4秒交接等待。评论筛选或回复准备期间，不插入故事。

实际互动结束后，旧续讲素材失效；无待回应互动时，结合已发送的聊天和书签生成带自然接回语的一份新正文，重新合成并编排动作。接回稿一旦投入准备，普通新事件在其后的选择机会处理。暂停／停止撤销未发送的正文和接回语，当前已开始的小段正常收尾；暂停不关闭弹幕互动。

主讲模型请求只使用本段 `topic.resume_required` 决定接回开头，不再同时传入全局 `current_topic`。接回段发送期间预备下一段时，下一段明确正常续讲；前驱中的接回语仅是上下文。全局接回待办仍等负责该次接回的段落完整发送后才清除，不因预处理而提前消费。

主讲书签只在完整发送和交接完成后推进，保留提纲、段落全文及发送记录，不能当作 Vidu 已播放完毕；当前系统没有播放完成反馈。未来主讲准备失败会单独标记，当前已开始的小段继续收尾，不自动付费重试。发送失败或结果不明继续停止后续处理，禁止自动重播。观众回复、一次安排及礼物欢迎在发送前失败时仅终止本条；筛选失败只消费该批，后续新内容继续，均不重试同一次收费请求。新场和服务重启不会自动开云场或恢复旧主讲。

输入区下方共用“待处理”和“回复记录”，每条内容仍标明主持安排或观众评论。回复记录中的“发给 Vidu 的指令”子折叠按需读取本场诊断日志，仅展示实际发送成功的 Type9 动作和 Type10 台词原文、发送时间及已有动作间隔；不会把计划当作已发送。发送成功不代表画面执行完成；读取失败或日志不完整会明确提示。

Q只发送眼神和表情，模型的 recovery 仅给出对应目标，例如“注视镜头”和符合本轮角色情绪的可见表情；不写姿态、肢体或过渡动作。Q 不承担身体归位，明确需要的主动返回保留在 S/L 中。发送节拍不变，实际表情延续与动作衔接仍需用户手动开停观察。

动作提示试用三行格式：`动作：…`、`眼神：…`、`表情：…`。Qwen3.8-Flash 继续输出原有 JSON 字段，程序统一编排后发送 Type9；这是文字组织方式，不是 Vidu 的新接口。主动动作及阅读前导保留动作、眼神、表情；Q只发送眼神和表情，不附带动作行。提示词要求保留原动作动词，默认一个必要动作，简写眼神和表情，减少额外步骤；明确要求的先后、等待和返回仍保留。离线检查只能验证格式与调度，画面理解和自然度仍需实播对照。

## 开一场

1. 保留 OBS 中的“御书房工作台”场景与本机浏览器源。宽 1080、高 1920；开启“通过 OBS 控制音频”，关闭“当不可见时关闭源”和“当场景变为活动状态时刷新”。其他场景需要相同画面时复用这一个来源，不能另建第二个接收者。
2. 确认百炼大脑配置就绪。筛选、回复、主持及同次TTS后的动作排程均使用 `qwen3.8-flash`，经百炼 OpenAI 兼容 HTTP 接口调用，显式关闭思考模式以减少实时互动等待。配置就绪只证明本机配置和凭据可读，真实可用性以模型回包为准。
3. 点击“开始会话”。它调用 Vidu 组件版，按平台规则产生费用；OBS 音画未就绪前不接收弹幕。
4. 可手动输入弹幕（最多五条在途），也可按下节连接真实评论。暂停会阻止新输入、清空候选并废弃未完成筛选；已进入回复队列的内容继续。只有还未交给大脑的条目可跳过。
5. 在 OBS 自行开始本地录制或公开推流。当前工作台不控制这些输出，也不把播放器在线等同于已录像。工作台的“结束会话”会停止数字人云场，必须回读云端结束状态。云端录像归档结束后可以新建下一场。

语音使用 Qwen Audio 3.1 Flash，未配置资产音色时默认 `libai_v3.1`。本机 `studio/data/local.json` 的 `tts_voices` 可按资产 ID 绑定音色；小恶魔 Lisa 当前绑定 `guyunshu_v3.1`。绑定在选择资产、新建会话及人工确认切换后生效，只影响新合成，固定回放仍使用原音频；状态接口的 `tts_voice` 可核对当前音色。顾云舒已生成独立试听，Vidu 场内听感仍需手动验证。底图与角色设定改由顶部“数字人资产”管理：空闲时保存角色语气、上传创建或选择开场资产；直播空闲时可发送切换，观察目标动态画面后再人工确认。整套阅读和直接接话继续由上下文自然选择；整套包含前倾、眯眼、1 秒后短读及回正，不拆成部位随机。

## 真实评论接入

1. 双击 `启动评论采集.command`，启动已经验证的浏览器版 dyhub 副本。只监听 `127.0.0.1:8757`；端口冲突时拒绝启动。它使用独立采集浏览器，不读取日常 Chrome 个人资料。
2. 在工作台“来源设置”填上述地址和自己抖音直播页地址末尾的数字 ID，保存后点击“连接评论来源”。订阅会触发 dyhub 开始采集；只有本场音画就绪、未暂停、发送保护未触发时，评论才进入候选池。
3. dyhub 持续逐条推送评论，程序先去重并检查时间。来源连接且会话就绪后，新候选立即唤醒筛选；筛选在途或回复队列已满时继续收集，模型完成或队列腾出位置后处理积压，每批最多 12 条评论，并结合礼物与欢迎一起选择；相似问题或连续补充可合并最多3条。两次实际筛选请求的启动至少间隔 1 秒，空池和繁忙不占用间隔；首批不再固定等待 5 秒，不补跑错过的定时批次。暂停、断连或全局发送／工作循环故障会清空候选并使在途筛选失效，恢复不重放旧评论，也不清除刚发生请求的限频。相关提问、动作请求、有意义接话优先；正常质疑吐槽可以回应，避免反复争执。模型可以整批不选。
4. 自动任务在途少于 2 条时才会继续筛选；候选最多 60 条，45 秒过期。模型结果回来、开始回复和第一段语音合成完成后都检查期限，避免旧评论补说；已经开始的短回复正常说完。未选中与重复评论不会进入真正回复队列。
5. “停止接收”关闭工作台自己的订阅，清空候选，不终止共享 dyhub 或已入队回复。结束云场会关闭订阅、取消未完成模型任务。真正退出采集服务，在它自己的终端按 Control-C。

筛选采用事件唤醒，保留原 0.25 秒维护检查，覆盖跳过回复等状态变化；采集回调只入池和唤醒，不等待模型。工作台页面仍每 2 秒刷新状态，这不影响后台接收与筛选。1 秒是筛选请求最小启动间隔，不是从收到评论到人物开口的时延保证；回复生成、TTS、动作编排和当前口播收尾仍按原流程执行。

真实评论以数据形式交给模型，没有工具权限；模型只返回候选 ID 或结构化台词/动作，由程序校验。昵称和原文以文本渲染。候选去重ID使用每次进程随机盐散列，未选中评论仅保留有界内存历史；选中评论与回复进入本场会话归档。

## 百炼大脑配置

正式模型为 `qwen3.8-flash`，北京工作空间，`enable_thinking=false`、JSON对象输出。官方资料：[模型](https://help.aliyun.com/zh/model-studio/qwen3-8-flash)、[OpenAI兼容接口](https://help.aliyun.com/zh/model-studio/compatibility-of-openai-with-dashscope)。

- 默认复用现有 TTS 的外部百炼 CSV 引用（`apiKey`、`workspaceId`、`apiHost`）；程序仅在服务端内存装载，不复制密钥、不写入前端或新配置。
- 可选 `data/bailian-brain.json` 只允许 `model`、`region`、`enable_thinking`，默认值分别为 `qwen3.8-flash`、`cn-beijing`、`false`。损坏或越界配置拒绝启动，不回退到旧模型。
- 请求地址由已校验的工作空间构造：`https://{workspace}.cn-beijing.maas.aliyuncs.com/compatible-mode/v1/chat/completions`。不允许重定向、任意端点或环境代理；运行依赖现有 `aiohttp`，无需安装 Node SDK 或百炼 CLI。
- 筛选与生成采用独立规则、上下文和用量统计；主持、回复和语音后的动作规划均计入“生成”。有多套合法排程时才增加一次请求，只有一套时直接采用并终检。
- 请求45秒超时，输入/响应有大小上限，失败不会自动重试；取消和关闭会结束本机在途HTTP请求，已经提交到云端的请求仍可能计量。修复后手动恢复只处理后续内容，不重发失败条目。
- 历史 `cloudbase_ai.py` 的 CloudBase 适配器和 `sdk/` 保留作原有测试与历史验证入口，正式工作台不再调用它；旧凭据及旧场次归档未删除。

## 故障与恢复

模型计划校验失败时，回复记录显示具体原因；本场 `conversation.json` 的对应条目保留 `plan_error`，`events.jsonl` 与诊断导出中的 `llm_plan_rejected` 记录条目 ID、失败阶段、拒绝原因和受限的返回结构摘要。摘要只含字段、类型、数量和长度，不保存原始返回文本或凭据。网络或模型调用失败仍保留独立错误码；失败条目不自动重试，恢复也不会重发旧条目。

- 控制台失联 35 秒、OBS 接收页失联 15 秒、模型持续异常或本机大脑工作循环失联 90 秒，或已就绪的视频帧停滞 15 秒，触发保护性停场。关闭页面不会保证立即停费，以云端回读为准。
- 刷新空闲的 OBS 页可重新领取资格；开始请求之后，同一场绝不换播放器或重入 RTC。发生连接故障时结束本场、核对结果，再显式新建。
- 创建结果未知、结束未确认会阻止下一场。不要删除标记绕过检查。日志和回执在 `data/runs/`，诊断导出经过脱敏。
- 页面保留最近 100 条；服务内保留最多 300 条弹幕，较旧的已完成记录写入本场归档。诊断内存环最多 300 条；播放器没有 MediaRecorder 或录像上传队列。云端录像以分块下载保存至磁盘。实际内存节省仍需同等时长实播对照，不能由结构变化推算数值。

## 正式语义动作流程（2026-10-31）

正常启动已启用 A 方案：“台词与短动作草案 → 同次语音时间戳 → Qwen3.8-Flash 最终排程 → GE/S/Q”，覆盖模拟弹幕、真实评论、主动安排和主讲话题。纯动作及显式试验/固定回放仍走各自原路径。

第一阶段生成台词和完整动作草案，原锚点仅表达语义意向。每段最多120字、最多6组，每组1–2个身体部位兼容的局部短动作；不接受 whole_body，模型不能把全身动作伪装成局部动作。普通单段语音仍限30秒。Qwen 合成后，程序校验时间戳与实际 PCM 一致，从已有词起点构造最多12套满足全部时间窗的完整候选；候选按原草案位置、句读起点和整体分布提供选择，不插值、不硬编码台词关键词。Qwen3.8-Flash 再读取真实时间戳与候选，只返回一个候选编号。候选多于一套时增加一次模型请求；唯一候选本地采用并经过同一最终校验，无动作不增加请求。

第二阶段只改变锚点，保持原台词、音频、动作、组数、顺序、眼神、表情和眼神表情目标。程序将独立GE提前1.1秒，S放在最终锚点，每组Q均安排在S后1.5秒，Q至下一GE至少1秒。因此相邻S至少相隔3.6秒；所有S必须取实际音频结束前的真实字起点，末组Q允许晚于语音结束。首GE可以在音频前预发。发送器在每次成功写入后重新计时，不追赶压缩间隔。1.1/1.5秒沿用已通过用户视觉评价的A样本，仍不是平台动作完成反馈。若整份音频找不到容纳全部主动动作的排程，在第二阶段模型调用前拒绝；模型返回未知编号也拒绝，不删动作、不补静音、不回退草案、不自动付费重试。

末Q越过音频尾时，音频进度门槛只要求真实PCM全部成功发送（包含最后一个样本），动作时钟仍等到原定Q时刻且距S成功写入至少1.5秒，不等待不存在的音频字节。下一段、下一任务和自动恢复D仍等待完整音频、既有缓冲等待与尾动作结束；停止会取消未发出的Q。只有正常对话A启用这项放宽，历史L、固定A/B和显式试验保持原规则。音频不会因此拉长或补静音，收尾自然度仍须用户实播验收。

动作描述允许在同一条Type9中表达自然连续动作，眼神与表情也允许自然连续变化；提示词与校验不再用“然后、接着、同时”或分号拒绝内容，也不要求因这些词强制拆节点。字段、类型、长度及A方案发送间隔检查保持启用；放宽文字描述不改变上述1.1/1.5秒编排，实际画面效果仍由试播验证。

2026-11-02 重组正式表演提示：共用任务定义置于最前，description描述该项完整画面，part用于本地身体资源协调。普通评论、统一编排评论、一次安排、主讲和无台词表演不再注入具体动作或题材示例；一次安排与主讲分别使用本模式规则。角色配置中完全相同的persona/reply_style只发送一次，不同值与名称继续保留；主持入口不携带阅读偏好。既有字段、部位、长度、阅读、主动返回及发送时序校验继续生效，历史专项提示与TTS后定位提示保持原样。离线回归验证了接入和合同；独立文字试验仍出现效果被改写成姿态，效果触发问题尚未解决，不能以提示重组或格式检查通过宣称实播成功。详见[本次变更与验证](../artifacts/prompt-refactor-20261102/变更与验证.md)。

时间戳必须与实际PCM哈希一致，保留单句起点、完整结束标志、流与下载音频一致、词时间及索引链检查。正式对话不再要求服务词表与原稿全文逐字相等，也不把服务索引跨度当成汉字数：例如“黢黢”可以是一个索引单元，词表和时间仍原样保留。每个候选及最终采用的动作短语必须在原稿和服务词表中唯一、连续、精确匹配，局部顺序可对应，并从服务已有词起点开始；异字处、重复歧义、跨标点或词内部均不猜测落点。无安全候选时明确拒绝；没有足够间隔的完整排程仍按原规则拒绝。模型选中后及实际发送前再次核验落点与音频绑定。历史固定回放继续保留全文与素材一致性检查。

有主动动作不会静默降级为语音；无主动动作仍可正常说话。短读继续使用实际短读PCM，并在短读和第一段回答都备好后才开始R/S0；短读回正后，回答使用同一A编排。取消、过期、停场、唯一播放器和云端结束回读保护保持启用。局部文字核验只证明落点具有可追溯的服务时间，不证明时间戳与真实发音或画面已经同步，仍需实播观察。

页面显示“口播默认动作：A方案”；运行状态、variant和run-mode归档记录A、S、1.1/1.5秒，固定回放另行标识。回复记录先显示草案，第二阶段完成后显示最终短语和计划时间；“编排动作中”纳入在途任务及取消保护。原始`plans`文件保留草案，每段另存`timed-action-input.json`、`timed-action-plan.json`、`timestamps.json`、安全SSE事件、合成结果及实际发送回执。模型等待中停止、换题撤销或首段过期时，不允许迟到结果发送；第二段失败保留第一段已发送证据。发送时间和离线测试不能代替画面同步验收；新台词、自动选点和不同动作的真实效果由操作者试用核对。
