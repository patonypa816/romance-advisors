# 评论、合并欢迎与礼物的统一编排方案

本文记录统一编排设计；不附私人运行证据。它替代旧方案的固定类别优先级与最多三人欢迎建议；礼物映射、信号约束及停场保护继续沿用，清唱仍待验证。

## 1. 核心决定

**一个大脑决定下一轮回应什么，本地程序保证公平、去重和发送秩序。欢迎以“一批人”为单位，人数增加不必让欢迎轮次同比增加。**

编排完成的标准为：这一轮计划中的动作指令、台词信息和音频等必要信号，已按规则全部发送完。以本地实际发送记录为依据，不以 Vidu 是否做出动作、观众是否看到或听到作为循环完成条件。

完成记账与下一轮允许发送是两个步骤：发送完更新记录；下一轮仍须通过现有音频发送锁、动作最小间隔和交接等待。等待只是发送安排，不命名为“确认动作完成”。

系统不承诺清空所有事件，也不承诺逐一点名。它应做到：低流量时及时接话，高流量时主动合并和取舍，有持续有效候选的类别不会一直被忽略。

## 2. 为什么要调整

持续评论可能占住准备机会，逐一点名欢迎会随人数线性增长；候选在准备期过期、入队即去重也可能造成从未欢迎的人失去资格。因此需要合并批次、明确完成边界和类别公平规则，不必重写底层发送器。这是设计风险分析，不是私人场次统计。

## 3. 收到的是候选素材，不是必须清空的任务

先校验、去重、整理，再交给编排器。采集回调不直接发送信号。

| 类型 | 如何整理 | 何时失去候选资格 |
| --- | --- | --- |
| 评论 | 同一人的补充可一起理解；相似问题可合并。使用用户 ID 区分同名观众 | 重复、已回应、明确略过，或已失去上下文时效 |
| 欢迎 | 确认是入场事件、荣誉／财富等级 ≥11、身份可识别、本场尚未完成欢迎。重复入场合并为同一待选人 | 尚未被选中时超过新鲜度窗口；不因此写入已欢迎集合 |
| 礼物 | 先消息去重，再按真实连击组归并；同一送礼者的多个待反馈项可以一起考虑 | 已反馈、规则关闭、明确限频／略过，或不再适合单独补谢 |

评论选择问题、招呼、玩笑、正常质疑或动作请求，不要求属于旧话题。避免同一人连续占用；“谁值得回应”由内容及近期回应记录决定，不按等级无上限排序。

礼物在连击收束或已有合并规则允许交接时进入可选状态；没有结束消息也不能永远等。缺少可靠组号时沿用明确限频，不假装已精确识别连击或累计数量。礼物名称与配置动作绑定，不让模型任意改写配置含义。

候选池有容量和时效边界。过期、合并、限频、失败和主动略过分别记录，不用“已回应”统称。容量限制导致的舍弃也不能静默冒充已欢迎。

## 4. 每轮怎样选择

每次有新的准备机会，本地程序提供：三类有效候选的摘要、近期回应对象、当前轮与已准备内容、各类等待轮数，以及现有动作规则。

大脑只决定一轮：主要目的、具体对象、回应内容，以及适合合并的次要回应。输出必须引用本地真实候选 ID／欢迎批次 ID／礼物组 ID，不能只靠一句“已欢迎所有人”扩大覆盖范围。

| 类型 | 什么时候选 | 对谁、怎样回应 |
| --- | --- | --- |
| 评论 | 当前轮进行时可准备，允许交接时发送；持续有评论也须让出其他类别的机会 | 选一个主要话题或对象，相似问题合并；避免连续只回复同一人 |
| 欢迎 | 自然衔接时选；达到公平保底时必须安排，不能等评论清空 | 少人可点名，多人以少量名字加集体欢迎覆盖一批 |
| 礼物 | 最近合适的选择机会优先考虑，不插断已发送或已承诺准备的内容 | 同组一次反馈，多人或同人多项可合并感谢，动作按配置及本轮长度取舍 |

一轮可以覆盖多类，例如：“阿青来了，玫瑰收到了。你问地狱也要加班吗？……”但必须自然、短小；严肃提问不必与感谢合并。每个被计作服务的类别，都要在计划中有对应回应内容或已配置的动作反馈，不能靠标签凑数。

集中送礼时，可以合并口头感谢、选一个合适的配置动作；未执行的其他礼物动作记为本轮合并取舍，不宣称逐个动作都已发出。若运营以后要求某类礼物必须逐项动作，应另行限定其触发频率，不能同时承诺无限接收与即时逐项处理。

没有有效互动时，按已有主讲／待机规则继续。长回答和故事在自然段间提供选择机会；既有人工控制与停止命令仍优先于自动编排。

## 5. 一条本地公平规则

**某类持续有可处理候选，却连续让过两轮，就进入保底；下一次尚未承诺的选择，优先照顾等待轮数最多的类别。** “两轮”是建议初值，可经回放调整，不是协议要求。

- 只以已完成发送的轮次更新正式等待计数。整轮完成且实际覆盖该类，计数归零；有有效候选却未覆盖，计数增加。没有候选时不累计额度。
- 多类同时到保底，先选等待更久的；并列时简单轮换，不长期固定偏爱礼物。可以自然合并，但不强塞三类进同一句话。
- 保底保证类别获得机会，不保证每个候选都被点名。欢迎可一次覆盖整批，评论仍要选取和略过。
- 待选欢迎因旧人过期、新人进入而持续存在时，不能重置类别等待数。只有池子确实没有可处理候选才归零。
- 准备失败、未发送或部分发送不计作成功服务；失败候选应有限重试或略过，不能让一个一直失败的项目卡住所有类别。不可处理的类别暂时不参与强制选择，恢复后重新参与。

提前准备需要一个边界：为下一轮选内容时，把当前轮预计覆盖的类别纳入预测，但正式记录等当前轮发完再更新。普通新事件不撤销已经开始的准备，因此保底约束的是**下一次还能改变的选择**，不是无条件保证“第三轮必播”。最多已有一轮承诺在前面；不能预备一长串内容绕开保底。发送前复核身份、场次、取消与重复状态，普通新事件留待下次选择。

## 6. 合并欢迎的完整生命周期

### 6.1 收集与确定批次

持续收集符合条件的入场者。空闲且人数少时不为凑批次强等；忙时自然积累。只有编排器确定本轮包含欢迎并提交准备，才冻结这一批成员。

本批包含提交时所有仍符合资格的待选人，以用户 ID 去重。冻结后成员进入本轮占用集合，从后续待选池排除；同一 UID 在此期间再次入场只合并记录，不能被下一轮重复选中。之后新进入且未被占用的人进入下一批。批次人数与台词长度分开：成员可以很多，通常只选 2–3 个名字作为代表，其余用明确的集体欢迎覆盖。模型只需批次摘要和代表昵称，不必输入全部名单；完整成员表由本地程序保存。

少人可以说：“欢迎阿青，进来坐坐。”多人可以说：“欢迎阿青、小林，还有刚才进来的各位朋友，进来坐坐。”

### 6.2 谁算被欢迎

点名式欢迎只覆盖明确点名的成员。合并欢迎必须在计划中明确标注批次，并包含面向该批的集体欢迎表达；本轮全部必要信号发完后，才统一提交完成记录，整批成员记为本场已欢迎并解除占用。混合轮也使用同一边界：欢迎段已发完而后续评论段失败，仍只保留已发明细，不提前把整批提交为完成。

只念两三个名字、没有集体表达，不能把整批算完成。模型临时说“所有朋友”也不能覆盖冻结批次以外的人。已被欢迎但未点名的人仍可在之后获得评论回复或礼物感谢，只是不再重复自动入场欢迎。

代表昵称从批次中轮换选择，兼顾可读性，不永久取最高等级或固定队首。无法安全、自然读出的昵称可不点名，仍可纳入集体欢迎。

### 6.3 超时与失败

普通候选的新鲜度期限只作用于尚未提交准备的成员。冻结批次进入一次有准备超时限制的正常准备／发送流程，不因跨过候选期限而半途消失；也不能永久占坑。

- 准备失败或取消且尚未发出信号：释放批次；仍新鲜者可重新成为候选，过时者略过。对同一失败原因采用有限重试，不无限重复生成。
- 部分信号已发送：记录哪些已发、哪些未发；不把整轮或整批标为成功，也不自动从头重放。批次进入“未完成结束”状态，解除成员占用，原事件不自动回到候选池；保留发送明细供去重，后续重新选其他内容。以后新的真实入场仍可重新评估，但应结合近期已发欢迎记录限频，不能因解除占用立即重复欢迎，也不能把旧入队状态当成本场永久屏蔽。
- 正常停止、换场：取消本场未完成准备和待选内容，迟到结果不能向新场发送。
- 候选过期但从未欢迎的人：以后再次真实入场，仍可成为新候选。“已进入池”与“已完成欢迎”使用不同记录。

新鲜度窗口可先保留现有 60 秒作比较基线，再根据回放调整。优先修复处理机会、批次粒度和冻结时机，单独延长窗口只会积压旧欢迎。

## 7. 在线名单与“停留两三秒”的能力边界

当前接口能力应按发布副本的 dyhub 事件合同理解：

| 需要的信息 | 当前能力 |
| --- | --- |
| 房间在线规模 | `room` 事件有 `total` 等房间统计字段；是统计值，不是人员表 |
| 谁刚入场、谁刚互动 | `member`、评论、礼物等事件含用户身份；只能证明收到过相应事件 |
| 当前完整在线名单 | 当前事件接口未提供 |
| 某个人已离开 | 没有已实现、已验证可用于维护人员在线状态的离开语义 |
| 某个人连续停留两三秒 | 当前不能可靠判断 |

依据：同级 `dyhub/src/pipeline/normalizer.ts` 的 member／room 分支、`dyhub/src/types/events.ts` 事件合同和 `dyhub/src/proto/douyin.proto.ts` 的 RoomUserSeqMessage 定义。原始 member.action 被保留，不代表非入场值都已验证为离场。

由于不能确认真实停留，不实现停留一两秒／两三秒条件，也不加入相应延迟缓冲。收到符合条件的入场事件后立即进入候选，按统一轮次编排与合并规则等待机会。

若入场两三秒后同一人又发来评论或礼物，可增加其“近期活跃”的选择依据，但仍不证明中间连续在线；不能因沉默判定离开，也不应强制所有人互动后才欢迎。用“欢迎刚才进来的朋友”，避免声称对方此刻仍在。

若以后要实现严格停留条件，需要另行验证可靠的人员在线状态来源：覆盖率、刷新时间、离开与重连语义。榜单、部分可见观众列表、没有收到离场事件，都不能替代完整状态。这是后续研究条件，不阻塞当前合并欢迎方案，也不等于断言平台永远无法提供此能力。

## 8. 稳定执行与清唱

最多保留正在执行的一轮，以及一个下一轮草案／准备结果。草案尚未投入内容或语音生成时可以调整；一旦提交准备，普通新事件留到之后。停止、换场、失效和准备失败仍可取消，不能用“稳定执行”绕开现有保护。

所有信号走已有唯一发送出口。保留 Type9 动作间隔、动作与语音配合、音频帧节奏及交接等待；Type10 台词紧邻动作不因此违反 Type9 之间的间隔规则。上一轮信号全部发送完成是记账事件，不能拿计划生成成功、TTS 成功或进入发送队列替代。

清唱如果后续声音验证通过，就作为一轮连续内容处理。唱四五句期间收集互动，不插入口播；短段结束、信号发送及交接条件满足后，重新按同一公平规则选择，优先结合期间积累的礼物和合并欢迎。评论也重新筛选，不按原始事件顺序逐条补课。清唱冻结的已承诺安排与单条语音一样，只保留有限下一轮，不预生成一长串。

本方案不增加动作视觉观察、姿态识别或播放完成回执。清唱是否像唱歌、声线是否一致仍属于声音能力验证，但不成为已发送信号的完成条件。

## 9. 必需记录与验证方法

只保留能由程序提供并影响决定的信息：候选身份与来源时间、有效／略过原因、批次成员、礼物组、最近回应对象、类别等待轮数、当前与下一轮状态、实际信号发送明细、失败／取消原因。没有来源的“当前画面”“仍在线”“实际动作完成”等字段不进入合同。

可复现的离线验证使用明确标注的合成事件，经生产准备与排程，把 Vidu 出口接到本地记录器，不需要为编排测试开云场。

| 场景 | 需要看到的结果 |
| --- | --- |
| 低流量 | 单个合格入场者可被欢迎，不为了多人批次长期等待；无候选时不空等 |
| 评论持续密集 | 欢迎到保底后进入尚未承诺的下一轮，不能靠持续预备评论绕开规则 |
| 礼物持续或三类同时繁忙 | 保底并列可轮换；评论、欢迎仍能获得机会；礼物同组不重复完整反馈 |
| 大批入场 | 少量代表昵称加集体表达覆盖冻结批次；新到者留到下一批；不生成无限长名单 |
| 准备时跨过候选期限 | 已冻结批次正常完成一次准备；取消／失败有明确去向，不永久占坑 |
| 重复入场与同名用户 | 已完成欢迎者去重；从未欢迎就过期的人再次入场可入选；同名不同 ID 不混淆 |
| 当前轮失败、下一轮已准备 | 正式计数不提前成功；下一次可变选择修正公平性，不循环撤销已付费准备 |
| 部分发送、停止、换场 | 保留已发明细，不把整轮算成功、不自动重放、迟到结果不进入新场 |
| 不使用停留条件 | 合格入场立即进入候选；不因不可确认的停留时间延迟，不写“在线已确认” |
| 清唱积累互动 | 若声音能力已通过，再验证歌后重新取舍与合并，不补播所有旧事件 |

同时统计每类最长等待轮数、等待时间、完成覆盖人数、点名人数、略过原因，以及发送轮次重叠和 Type9 最短间隔。“整批被覆盖”和“每个人被点名”必须分别统计。

实施顺序建议：先统一选择入口与公平规则；同时修欢迎批次和完成去重；再做低／高流量及失败回放；最后调两轮保底和新鲜度等参数。清唱声音验证独立推进，不阻塞当前评论、欢迎、礼物编排。

本次实现包含统一选择、有限提前准备、公平计账、欢迎批次、混合轮及界面覆盖人数。感谢与欢迎保留配置模板；合并评论由大脑生成一段回复。纯动作礼物若没有独立欢迎前导可承载动作，则与评论拆轮，避免覆盖观众明确请求的动作。普通事件不撤销已准备轮；人工主持明确插队保留既有控制优先权。清唱尚未接入；本地回放不需要真实抓取或Vidu云场，也不证明真实平台与视听效果通过。
