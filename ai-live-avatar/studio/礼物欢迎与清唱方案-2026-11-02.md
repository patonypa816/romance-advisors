# 礼物、入场欢迎与短句清唱

> 后续调度以[统一互动编排方案](统一互动编排方案-2026-11-02.md)为准。本文保留礼物映射、协议边界与清唱验证方案；固定轮间优先级不再作为现行调度依据。编排循环以必要信号发送完成为标志，不依赖人物动作观察。发布副本不包含私人联调记录或录像。

## 本轮约定

- 礼物反馈：工作台可配置“礼物 → 动作”，先设计一套默认规则，后续可以修改。
- 入场欢迎：用户所说的“抖音直播用户等级”暂按荣誉／财富等级解释，严格大于 10，即 11 级及以上。不是粉丝团等级。
- 唱歌：输入歌词，让角色用与说话一致的声音清唱四五句；不需要完整歌曲、伴奏、环境音或其他配音。
- 清唱期间收到的礼物和符合条件的入场事件先收集，唱完后统一感谢、欢迎。
- 除后续单独授权的评论筛选触发方式外，回复、主讲、原有 A 动作编排及停场保护沿用现状。

## 礼物默认规则草案

以下是我们设计的反馈，不是抖音要求的动作，也不是已经验证过的 Vidu 动作。礼物名称是预设示例；当前直播间的准确名称和 ID 要根据实际采集结果绑定，不根据网络价格表猜测 ID。

| 礼物示例 | 动作意图 | 一句感谢的内容 | 建议用途 |
| --- | --- | --- | --- |
| 小心心 | 看向镜头，微笑，轻点头一次 | 谢谢昵称的小心心，心意收到了 | 轻量反馈 |
| 玫瑰／鲜花 | 一手轻放胸前，略微颔首 | 谢谢昵称送来的花 | 温和致谢 |
| 棒棒糖 | 笑着竖起一个大拇指 | 谢谢昵称，这份甜收到了 | 轻松互动 |
| 大啤酒 | 轻抬一只手，向镜头致意 | 谢谢昵称，心意领了 | 不凭空生成酒杯或酒瓶 |
| 加油鸭 | 轻握拳，做一次鼓劲动作 | 谢谢昵称，咱们一起加油 | 鼓励型互动 |
| 比心类礼物 | 单手做一次小幅比心 | 谢谢昵称，给你比个心 | 手势须先试播 |
| 热气球／飞机类礼物 | 目光略抬，再向镜头挥手 | 谢谢昵称送来的礼物 | 名称逐项绑定，不用模糊关键词匹配 |
| 嘉年华／烟花类礼物 | 笑意加深，双手适度展开，再致意 | 谢谢昵称，这份心意记住了 | 稍完整的庆祝，保持原坐姿 |
| 未配置礼物 | 微笑点头 | 谢谢昵称送来的礼物 | 可关闭的兜底规则 |

感谢措辞可按当前人设变化；礼物对应的动作意图由规则确定。动作编排仍经过已有的身体部位、时序、回正和发送校验，不把观众昵称或礼物名称当成控制指令。

建议每条规则可编辑：启用状态、礼物 ID、显示名／明确别名、动作描述、感谢方式（动作＋一句话／只做动作）、冷却时间。具体冷却值属于后续试播可调的产品参数，不是协议要求。

### 连击与重复事件

1. 先按消息 ID 排除重复传输。
2. 对同一房间、同一用户 ID、同一礼物 ID、同一有效连击组 ID 合并。进度帧和结束帧通常不是同一个消息 ID，只有消息去重不够。
3. 一组连击安排一次完整反馈；尚在队列中时更新数量，结束帧不再创建第二个动作。已经反馈后，不因同组后续数量增加不断追加动作。
4. 若来源字段表示累计数量，1、2、3 的进度不能累加成 6；按同组累计最大值更新。不要未经真实样本核对就把 repeatCount、comboCount、groupCount 相乘。
5. groupId 缺失、为空或为 0 时不能声称已可靠识别连击。仅消息 ID 去重不足以保证一次动作，应标注数量／分组未核实并采用明确的限频策略；不伪造精确总数。
6. 不根据价格拉大动作，也不自动把礼物映射成收费歌曲生成。清唱是否由礼物触发不在本轮已约定范围内。

官方直播玩法推送说明明确存在重复和非绝对时序；它与当前 dyhub 的私有协议不是同一接口，字段不能混用。官方伴侣接口使用 sec_gift_id，当前 dyhub 使用 giftId，两套 ID 也不能直接替换。

来源：[抖音数据开放说明](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/develop/server/live/danmu)、[官方伴侣礼物池接口](https://partner.open-douyin.com/docs/resource/zh-CN/live-interactive-tools/development/tutorial/live-tool-guide)、[DyHub 事件协议及连击说明](https://github.com/ymstar/dyhub#-事件协议)。

## 11 级及以上入场欢迎

采集器和工作台包含所需字段，可用合成二进制样本核验字段路径；真实等级与入场语义仍需操作者在获准场景单独验证。

- 逆向协议中的目标字段为 User.payGrade（字段 23）→ PayGrade.level（字段 6）；不要使用含义不明的 User.level（字段 6）代替。
- 补出 MemberMessage.action（字段 10）、isSetToAdmin（字段 5），可同时保留 enterType（字段 9）。现有第三方采样说明将 action=1 标为入场，但还需本人房间核验。
- 等级缺失或入场语义未知时不自动欢迎，不回退到粉丝团等级或按昵称猜测。
- 以用户 ID 去重；建议同一用户本场只欢迎一次，支持配置重复入场冷却。不同用户同名不能合并。
- 多人同时进入可合并为一句欢迎，避免连续点名挤占口播；不在欢迎词里朗读等级数值。
- 清唱期间保留待欢迎项，歌后合并；普通过期欢迎不在很久以后补说。停场和换场清空待处理事件。

协议证据来自第三方逆向项目，不是抖音官方稳定性承诺：[User/PayGrade](https://github.com/saermart/DouyinLiveWebFetcher/blob/main/protobuf/douyin.proto#L438-L483)、[MemberMessage](https://github.com/saermart/DouyinLiveWebFetcher/blob/main/protobuf/douyin.proto#L209-L230)、[采样说明](https://github.com/opedium/douyin-live-proto/blob/master/docs/complete_payload_reference.md#webcastmembermessage)。

## 四五句清唱：先验证声音，再接工作台

当前正式口播使用 qwen-audio-3.1-tts-flash / libai_v3.1。第一步应复用同一音色，只对独立小样使用清唱指令，以四句自写歌词检查：有连续旋律而非朗读、角色声线一致、歌词完整、没有伴奏和环境音。建议先以约 15–30 秒为测试范围；这是试验范围，不是已确认能力或强制生成时长。

百炼文档确认 instruction 能控制说话方式，未明确保证该音色支持清唱、音符或指定歌曲旋律。不能把“提示词里写了唱歌”或“返回了音频”当成通过。若小样只是朗读，停止这条实现路径，再评估可保留角色音色的专门歌声方案；不静默切换歌手声音或输出背景音乐。

仅输入歌词也不能保证复现某首已有歌曲的旋律。当前方案只以“四五句像角色本人清唱”为目标；如果后续要求准确唱某首歌的原曲，需要另行确定旋律输入与验证。

Mureka 虽支持 vocal_id 条件生成，但该 ID 不能复用百炼 voice ID；其显式歌曲时长控制为 120–300 秒，输出人声还涉及分轨，不能当作本需求的简单默认方案。此次不接整曲服务。

来源：[百炼实时语音合成及指令控制](https://help.aliyun.com/zh/model-studio/realtime-tts-user-guide)、[Mureka 歌曲生成](https://platform.mureka.ai/docs/api/operations/post-v1-song-generate.html)、[Mureka 声音克隆](https://platform.mureka.ai/docs/api/operations/post-v1-song-vocal-clone.html)。

## 信号发送的最小扩展

所有类型仍共用唯一音频／动作发送出口，新增事件不直接从采集回调向 Vidu 发信号。

- 评论继续走原候选池。采用事件触发筛选，两次请求启动至少间隔1秒；礼物、欢迎已有实现，清唱尚未实施。
- 礼物与入场交独立的有界事件队列，校验、去重后等待下一轮发送资格。
- 正在执行的口播或动作按原规则收尾，主持的既有优先级保留。新互动的建议轮间顺序为：礼物反馈、原已选弹幕、合并欢迎、备用主讲；原有类型的相对顺序不变。
- 清唱是独立的一轮表演，占用现有唯一发声通道；期间只累计礼物和欢迎，不插入口播或礼物动作。清唱后的反馈完成后，再按原有规则续讲。
- 清唱使用同一份连续 PCM。不能把四五句逐句套普通发送器，否则每句末尾现有 4 秒缓冲会打断歌声。只在片段末尾交接一次。
- 声音生成通过后再处理口型测试。Vidu 官方外部音频格式为 24kHz、单声道、s16le PCM；当前发送器每 100ms 发送一帧，可复用底层节奏。
- 清唱不直接复用口播的逐词动作时间戳；第一版只安排必要的开始／结束姿态，避免把长音误当成普通说话字点。
- 本机发送完毕不等于云端播放完毕。歌后开始感谢的实际间隔需看回传画面和声音验证，不能把固定缓冲宣称为播放完成回执。
- 现有“结束会话”仍结束整场。若增加“停止清唱但保持会话”，需独立验证 Type7 打断、剩余缓存和恢复口播；不能复用全场停止并声称只是停歌。

源码接入点：`dyhub_client.py` 的订阅／字段白名单、`automation.py` 的 on_event 分流、`director.py` 的轮间选择、`live_session.py` 的准备／发送分支、`motion_component.py` 的同一音频锁，以及 `static/index.html` / `app.js` 的新增设置入口。采集器位于同级仓库目录 `dyhub/`，启动脚本运行 dist，修改源码后需要对应构建。其中 gift/member 白名单、事件队列、轮间调度、统一发送器与界面已完成本地实现；清唱相关准备／发送分支仍未修改。

Vidu 来源：[组件版接口](https://platform.vidu.com/docs/api-reference/digital-human/realtime-avatar-component)。

## 实施与验收顺序

1. 先做独立四句清唱小样，确认同音色清唱能力；不需要为声音试验开启 Vidu 云场。
2. 补 gift/member 字段和离线二进制／事件回放验证，再接可配置规则与唯一发送队列。保持普通评论原回归用例。
3. 加界面配置和模拟礼物、模拟入场工具，验证连击只反馈一次、10级不欢迎／11级欢迎、等级未知不猜、重连不重播、停止后迟到结果不发送。
4. 在用户手动开启的本人直播间核对真实等级和礼物样本；dyhub 文档说明礼物采集涉及登录态，当前登录状态和礼物完整性仍须确认。
5. 声音小样通过后，再在工作台验证四五句清唱口型、歌后感谢与欢迎，以及原口播恢复。不能以离线测试或“发送成功”替代画面和听感验收。

推荐顺序：先验证评论事件触发、本地礼物／欢迎规则和模拟工具，再单独验证同音色清唱。真实采集、动作画面和清唱听感不能由离线测试替代。
