# M3 创意赛实现契约 (2026-11-01)

Baseline: final M2 `a80ab7`. This describes implemented interfaces, not verification evidence. One application, PostgreSQL, text-only protected operator page, simulated/local-test identities. Native ChatGPT manual export/import stays; no external model client, BaiLian, money, automatic programming, interview prerequisite, real audience claims.

## Frozen test defaults
`m3-nightmare-product-test-v1`, explicitly test_only: “为噩梦研发部设计一款荒诞但能实际说明用途的噩梦产品：写出名称、核心体验，以及客户投诉后的补救办法。” 1–1000 Unicode characters (raw whitespace preserved, nonblank); max 12 distinct authors; revise freely before close, one final work each. Submission window 300 seconds; voting 120 seconds; review attempt 900 seconds. Manual early close supported; server deadlines authoritative, right-exclusive.

Rule snapshots freeze at create. Author eligibility, name and employee/guest membership are captured at FIRST ACCEPTED SUBMISSION. A player registered after opening may participate. Revisions preserve the original participation snapshot, including after later hiring. No interview check or employee requirement. Voter eligibility = registered world players at FIRST ACCEPTED VOTE, whether authors or not, including registration after voting opens; one vote per voter, self-vote allowed (explicit test default), revise target before close, no abstention deletion endpoint. Final candidate order = first accepted submission sequence, then canonical submission UUID (deterministic).

Rubric criteria exactly `originality`, `coherence`, `setting`; integer scores 0–2 each. Definitions: originality 0 no concrete novel product, 1 concrete product with one unusual feature, 2 a distinct mechanism plus an unexpected consequence; coherence 0 no usable explanation, 1 coherent experience/use, 2 coherent experience plus actionable complaint remedy; setting 0 no nightmare/company setting, 1 clear nightmare product, 2 nightmare and workplace/customer-service motifs materially integrated. Scores describe game work, not real personality. Positive criterion requires 1–2 exact original-text substrings, each 1–120 chars; zero requires empty evidence. Nonempty reason 1–160 chars. Separate `comment` 1–160 chars: descriptive short paraphrase, no score/rank/comparison/winner predictions. Comment is not sufficient to infer semantic quality; native review inspection remains necessary.

AI creativity winner = max total; tie earliest final candidate order. Popularity winner = max frozen vote count if total votes > 0, tie earliest final candidate order; no votes means no popularity award. One author may win both. Guests receive only named nonmonetary award/history. Employee-at-first-submission winners get +1 performance per award, at most +2 for the round; no other attribute/currency/company metric changes. Store actual before/after and delta. Everyone gets participation final event, not everyone an award. Eligibility does not change if an interview changes membership later. Apply employee reward only if frozen employee and current membership employee, otherwise fail settlement as invariant violation, not silently drop. Current code has no demotion. No balance/global cap invented.

## State machine
READY -> `open` (operator confirms prompt presented) -> SUBMITTING -> `close-submissions` or deadline -> REVIEWING with final texts/revisions/eligibility frozen and per-work tasks created. Zero works -> EXPIRED, no settlement. All tasks accepted -> DISPLAYING automatically. Any failed/interrupted/expired task -> WAITING_REVIEW; still-running other work results may be accepted here. Only failed/interrupted/expired tasks retry. Successful tasks immutable and never rerolled. Once all accepted -> DISPLAYING. No display content or votes before all valid work accepted.

DISPLAYING -> per-work `confirm-display` (operator explicitly confirms this work AND descriptive comment were rendered on local development page) -> `open-voting` only when every frozen candidate confirmed -> VOTING -> deadline or `close-voting` -> READY_TO_SETTLE -> `settle` -> COMPLETED. Manual settlement keeps failure recovery clear. UI does not claim external viewers saw/heard anything. Before votes close/settlement, hide scores, criterion reasons/evidence, totals, ranks, live vote counts and awards from ordinary round snapshot; protected evaluation export/import is operator tooling, not public display. Display order fixed, not score sorted. All evaluations can be revealed on COMPLETED only. UI must render full work+comment before enabling its explicit confirmation control.

Pause from nonterminal states retains `paused_from`; all currently running review attempts become interrupted (accepted unchanged). Restart/DB recovery persistently pauses every active competition. Resume SUBMITTING/VOTING resets complete test window; resume REVIEWING/WAITING_REVIEW -> WAITING_REVIEW and explicit per-work retry required; other states restore source. No auto resume, auto reward or replayed display acknowledgment. Cancel any nonterminal state with 1–200 char reason; retain every draft, vote, review and confirmation, no settlement/reward. No per-work technical exclusion. In this minimal slice, illegal content discovered at any time before settlement requires cancelling the round with reason (pre-display selective disqualification/refreeze deferred); after settlement needs future explicit compensation, never editing ledgers. This is a conservative subset of SPEC, not silent exclusion.

## Exact HTTP surface
All existing HttpOnly session, same-origin write protection and database/mutex gates apply. No new public write or identity/role system. Paths `GET /api/competitions` (last 20), `POST /api/competitions` `{command_id}`, `GET /api/competitions/{id}`. Lifecycle POST `/api/competitions/{id}/{open,close-submissions,open-voting,close-voting,settle,pause,resume}` `{command_id,expected_version}`; `/cancel` adds `reason`.

POST `/{id}/submissions` `{message_id,player_id,expected_submission_revision,text}` (revision 0 create, current positive integer revise); reject stale author revision with stored business rejection. A new message with same text is still a new revision. Submission identity stays stable; retain all revision records `{revision,message_id,text,admitted_at}`. POST `/{id}/votes` `{message_id,player_id,submission_id,expected_vote_revision}` (0 first, current revision change); retain changes `{revision,message_id,submission_id,admitted_at}`. No world/round expected_version for ingestion (other authors must not invalidate this author).

GET `/{id}/vote-state?player_id=UUID` returns exactly `{player_id,vote_revision,submission_id}` for a registered player in the same world (revision 0 and null target before their first accepted vote). This protected operator route reveals no tally or scores and enables reload/change-vote. It is not a public voting identity/authentication system.

GET `/{id}/submissions/{submission_id}/evaluation-request` returns current running attempt only: `{task_id,attempt_no,input_hash,policy_hash,frozen_input}`. `frozen_input={rule,policy,submission:{id,revision,text}}`; no mutable round/world version binding. POST same prefix `/evaluation-result`: `{command_id,task_id,attempt_no,input_hash,policy_hash,evaluation}` where evaluation exactly `{criteria:[{id,score,evidence,reason}...],comment}`. No expected_version here: another work finishing must not stale this attempt. POST same prefix `/retry` `{command_id,expected_version}`. POST same prefix `/confirm-display` `{command_id,expected_version}`.

Strict UUID, true integers, JSON rejection, canonical typed content hash and raw-preserving validation follow M2. Never accept extra `total`, `winner`, reward or metadata keys. Hash all immutable task input/policy. Business command failures (404/409 CompetitionError) reserve original receipt, malformed initial request does not; malformed evaluation on a matching active envelope records failed attempt/receipt and WAITING_REVIEW atomically. Wrong task/attempt/hash/state cannot alter current valid task. Timeout transitions failure, no zero. Duplicate same ID/payload replays before version/deadline checks; altered target/action/typed payload returns 409 command_conflict. Input replay namespace reuse existing input_records (action+competition ID in payload prevents M2 cross-action reuse).

Command receipt `{command_id,replayed,revision,competition}`. Input receipt `{input_id,accepted,rejection_code,replayed,competition_id,revision,submission_id,submission_revision,vote_revision}` with unrelated fields null. GET single `{revision,server_time,competition}`, list `{revision,server_time,competitions}` in one REPEATABLE READ transaction. UUID lowercase; timestamps UTC ISO8601. Expected version uses per-round `version` >=1.

Competition snapshot:
```
{id,version,status,paused_from,pause_reason,rule,opened_at,deadline_at,
 submissions:[{id,player:{player_id,display_name},revision,text,submitted_at,
   task:{id,status,attempt_no,deadline_at,error_code}|null,
   comment:null|string,display_confirmed_at:null|string,
   evaluation:null|{criteria,total}}],
 votes:[{player_id,submission_id,revision}]|null,
 result:null|{settlement_id,awards:[{player_id,submission_id,award_type,performance_delta}],
   rankings:[{submission_id,total,votes}],completed_at},allowed_actions:[]}
```
All work text visible in protected submission operator view during SUBMITTING, but no audience/display view until DISPLAYING; simplest UI separates admin entry/work list from disabled display panel. comment null until all reviews accepted; evaluation and votes null until COMPLETED (individual vote revision available only in protected vote-state and input receipts). Export endpoint intentionally returns operator-only raw frozen work. Allowed actions authoritative and state-scoped; frontend uses exact state, no inferred advance.

Errors M2 style: 400 validation_error; auth unchanged; 404 competition_not_found/player_not_found/submission_not_found; 409 command_conflict/version_conflict/state_conflict/active_competition_exists/evaluation_expired/not_all_displayed. Input business rejections HTTP 200: not_eligible, capacity_reached, stale_submission_revision, stale_vote_revision, invalid_candidate, paused, deadline_passed, not_open. Never accept deadline equality even if timer is late.

## Minimal persistence and transaction boundary
Schema 3 additive; explicit migrate accepts empty/1/2/3 and preserves all M1/M2 rows/receipts, idempotent rerun; startup demands 3. Existing model_tasks/settlements/game_events are interview-FK-specific: avoid risky universal redesign.

New tables: `competitions(id,world_id,status,version,body JSONB,created_at)` with partial unique active-world index; `competition_commands(world_id,command_id,payload,response,created_at)`; `competition_settlements(id,world_id,competition_id UNIQUE,payload_hash,result,created_at)`; `competition_reward_ledger(settlement_id,player_id,award_type,before JSONB,after JSONB)` primary unique triple; `competition_events(competition_id,player_id,world_id,event_type,payload,created_at)` unique round/player. JSON body owns full frozen rule/policy, author/voter eligibility snapshots, draft revisions, final candidate snapshot, vote revisions/frozen tally, task frozen_input/hash/current attempt/history including accepted evaluations, display confirmations and result. No task queues or extra universal tables. Bounds (12 works, 1000 chars) keep this acceptable; retain sources not only derived winners.

Every mutation lock world row then read PostgreSQL clock_timestamp, lookup receipt, load phase, apply; no model/network calls while locked. Same app gate serializes HTTP command/timer/startup pause across M2/M3; failure gate must protect competition too. One active competition even WAITING_REVIEW/PAUSED. Independent M2 may run while a competition waits; no dependency between activities.

`RecordService.apply_competition_result(conn,world_id,competition_id,frozen_plan)` neither begins nor commits. Plan deterministically calculated by game code only after frozen votes; hash includes final works/accepted evaluations/tallies/eligibility/rule/awards. Existing identical settlement returns original; differing plan conflicts. In SAME transaction: save frozen vote state as needed, unique settlement, all award ledger rows (guest named awards zero asset delta), eligible membership performance updates, one competition event per participant including earned awards, round COMPLETED/result, world revision, command receipt. Failure anywhere rolls everything back, including phase changes and successful receipt. Cancellation/expiry/failure never awards. Profile query merges M2 and competition events chronologically, preserving existing recent-10 semantics. No company asset mutation; state explicitly “company delta none”. DB exception before/after commit retries with original ID only.


## Implementation notes and service boundary

`CompetitionService(engine, world_id)` exposes `start(data)`, `command(id, action, data)`, `submit(id,data)`, `vote(id,data)`, `vote_state(id,player_id)`, `evaluation_request(id,submission_id)`, `evaluation_result(id,submission_id,data)`, `submission_command(id,submission_id,action,data)` for retry/confirm-display, `get(id)`, `list_competitions()`, `recover(reason='restart')`, `expire_due()`.

`rule.prompt` holds the prompt. Task states are `awaiting_result`, `accepted`, `timeout`, `invalid_schema`, `invalid_evidence`, `interrupted`. Retry accepts only the last four states during REVIEWING/WAITING_REVIEW; accepted work remains immutable. Round allowed actions use `submit`, `vote`, `confirm-display`, `retry` for the respective per-item controls. Evaluation export remains possible for pending tasks in either review state.

The validator enforces strict keys/types/score bounds/exact quotes and comment length. A narrow pattern flags possible score/rank/winner language for human review, without discarding the accepted evaluation; it cannot determine semantic meaning or prove that an unflagged comment is neutral. Comment semantic neutrality, rubric quality and content suitability require native/manual review. confirm-display attests the operator checked non-scoring descriptive commentary and rendered the full work plus comment on the local page; it does not attest public broadcast. If a work or comment is unsuitable, cancel the entire unfinished round; there is no selective exclusion or accepted-result reroll endpoint.

Only protected local operator UI/API exist here. No claim of real audience exposure, real identity proof, production access control roles, external AI API, or persistent production deployment. M2 remains independent and available while M3 waits.

Verification results belong in acceptance evidence, not this contract.
